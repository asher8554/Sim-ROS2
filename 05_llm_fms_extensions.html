1. LLM + OpenAI API: 자연어 → Structured Command (16강)

핵심 개념

LLM은 로봇을 직접 움직이지 않습니다. 한국어 문장을 RobotCommand라는 정해진 형식(의도 하나 + 슬롯)으로 바꾸는 일만 맡고, 그 결과가 실행 가능한지는 코드가 한 번 더 검사합니다.

한국어 문장→LLM (Structured Output)→스키마 검증 (pydantic)→세계 검증 (validate_world)→실행 / 되묻기 / 거부
스키마 검증
JSON 스키마는 형식만 보장합니다. Intent·Place가 Enum이라 목록 밖 값은 나올 수 없습니다.
세계 검증
의미(옮길 수 있는 컵인가, 목적지가 있는가)는 validate_world가 검사하고 문제를 한국어 문장 목록으로 돌려줍니다. 빈 목록이면 실행 가능합니다.

구조: 의도 8개와 슬롯

필드내용
intentmove_object · go_to · find · report · answer · arm_pose · gripper · stop (8개). answer는 움직이지 않고 말로 답 · 되묻기 · 거부
target물체(cup_pink 등) · person · 자세(ready, hands_up, transport, home) · 그리퍼(open, close)
source / destinationPlace Enum ('' · home · drinks · consult_1 · consult_2 · info ...). 출발지가 비면 drinks로 채움
reply사용자에게 할 한 문장 (되묻기 · 거부 포함)

필드의 description도 스키마에 실려 모델에게 전달되므로 필드 설명이 곧 프롬프트입니다. 컵은 마커가 있는 세 스테이션(STATIONS: drinks · consult_1 · consult_2) 사이에서만 옮길 수 있습니다.

프롬프트는 세 부분입니다. SYSTEM(장소의 한국어 별칭 · 기본값 · 판단 규칙, 색 · 목적지가 없으면 추측 금지 → answer로 되묻기, 위험한 요청은 answer로 거부), few-shot EXAMPLES 4개(실행 명령 · 팔 자세 · 찾기 · 되묻기), 그리고 이번 문장입니다. 파싱은 temperature=0.0으로 부릅니다.

# src/warehouse_lecture/warehouse_lecture/llm/client.py  LLM.parse 핵심
response = self.client.chat.completions.parse(
    model=model,                      # llm.yaml: gpt-4.1-mini
    messages=messages,
    response_format=schema,           # pydantic → JSON 스키마 → 응답이 따르게 강제
    ...)
message = response.choices[0].message
if message.refusal:
    raise ValueError(f"Model refused: {message.refusal}")
return message.parsed                 # 검증이 끝난 RobotCommand 객체

항목값

defaultstemperature 0.2 · max_output_tokens 800 · timeout_s 30 · max_retries 2
pricing (USD / 1M 토큰, 추정용)gpt-4.1-mini input 0.40 / output 1.60 · gpt-4.1 input 2.00 / output 8.00
usage_loglogs/openai_usage.jsonl (호출마다 JSON 한 줄, purpose로 출처 구분)

  • 03_accuracy.py의 score는 intent가 같고, 테스트에 적힌 슬롯만 비교합니다. 되묻기(ambiguous) · 거부(refuse) 문장은 intent=answer에 더해 reply가 있어야 정답입니다.

  • 프롬프트와 예시가 매번 함께 가므로 명령마다 입력 토큰이 일정하게 듭니다.

2. LLM → ROS 2 Task Pipeline: 문장 하나를 단계 목록으로 (17강)

핵심 개념

"손님께 음료 가져다 드려"처럼 여러 동작이 필요한 문장은 명령 하나로 표현할 수 없습니다. LLM이 RobotPlan(단계 목록)을 만들고, 코드가 계획을 머릿속으로 따라가며 검증 · 보정한 뒤, Task Manager가 /execute_plan 액션으로 단계를 차례로 실행합니다.

문장→PlanParser (LLM)→RobotPlan.validate_world→PlanDialogManager (되묻기 · 확인)→/execute_plan (Task Manager)→Nav2 · PickPlace

구조

요소내용
StepActionnavigate · detect · pick · place · arm_pose · gripper · report · answer (8가지). 관절 · 속도는 LLM이 건드리지 않음
PlanStepaction · target · location · note. location은 navigate=목적지, pick=컵이 있는 곳, place=놓을 곳
RobotPlansummary · steps · reply. steps가 비면 실행 없이 reply만 말함 (되묻기 · 거부 · 답변)

프롬프트 규칙의 핵심은 "컵을 옮기는 일은 항상 네 단계"입니다. navigate(컵이 있는 곳) → pick → navigate(도착 테이블) → place. 컵 색은 골라도 되지만 도착 테이블은 추측하지 않고 되묻습니다. 여러 잔이면 컵마다 네 단계를 반복합니다(한 번에 컵 하나).

계획 검증: here 와 held

단계검사 · 보정
navigatehere = 지금 위치 갱신
picklocation이 비면 지금 스테이션, 아니면 drinks로 채움 · 이미 들고 있으면 problem · here가 다르면 navigate 단계를 자동 추가 · held = 든 컵
place놓을 곳이 없으면 problem(기본값 없음) · 든 것이 없으면 problem
끝든 채로 끝나면 problem (place 단계가 없다)

대화와 실행

  • PlanDialogManager.handle: 확인 대기(pending) 중이면 응 → 실행, 아니 → 취소. 되묻던 중이면 앞 문장과 /로 이어 붙여 다시 계획합니다("손님께 음료 가져다 드려 / 2번 테이블").
  • pick · place가 든 계획만 번호 목록과 "진행할까요?"로 확인하고, 이동 · 보고뿐인 계획은 바로 실행합니다.
  • Task Manager는 서버에서 validate_world를 한 번 더 실행하고, 단계마다 피드백 발행 + 취소 확인을 합니다. 한 단계라도 실패하면 뒤 단계는 실행하지 않습니다.
  • pick 단계는 앞 장의 PickPlace 액션을 phase="pick"으로 호출합니다(도킹 · 집기 · 들기까지).

3. Web FMS: 브라우저 한 화면에서 주행 · 카메라 · LLM 지령 (18강)

핵심 개념

FMS 서버(fms/server.py)는 ROS 2 노드(robotworld_fms)이자 Flask 웹 서버입니다. ROS 콜백이 상태 사전 self.s에 쓰고, 브라우저는 SSE로 그 상태를 받으며 HTTP API로 명령을 보냅니다. 쓰는 스레드와 읽는 스레드가 달라 잠금(lock) 하나로 보호합니다.

ROS 토픽 (/amcl_pose, plan, /odom, /scan, 컵)→put() → self.s→/api/stream (SSE, 0.2 s)→브라우저 EventSource
브라우저 버튼 · 지도 · 채팅→HTTP API→/cmd_vel · Nav2 goal · /execute_plan

/cmd_vel 을 쓰는 세 가지와 기능별 흐름

기능동작
수동 조작 (dead-man)버튼을 누르는 동안 150 ms마다 /api/drive. 서버는 0.1 s 타이머로 발행하고, 요청이 0.4 s 안에 다시 오지 않으면 0을 한 번 보내고 정지. 속도 제한 0.3 m/s · 0.8 rad/s. 첫 요청이 Nav2 goal · 미션을 먼저 취소
장소 버튼 · 지도 클릭NavigateToPose goal(frame map). 장소 버튼은 locations.yaml의 base_goal, 지도 클릭은 클릭 좌표. 미션 실행 중에는 거부
LLM 지령앞 절의 PlanDialogManager를 그대로 사용. speak만 채팅 기록으로, executor만 /execute_plan 호출로 교체. world=self.world_state로 컵 위치표가 프롬프트에 들어감
정지/api/stop → cancel_all. FMS가 보낸 Nav2 goal과 Task Manager 계획을 둘 다 취소(PickPlace · Nav2까지 취소가 내려감)
카메라/dev/shm/robotworld_fms/enabled 파일이 있을 때만 JPEG 저장(원자적 교체). 서버가 MJPEG /camera/head_camera.mjpg로 스트리밍 → 영상이 ROS 토픽을 거치지 않음
# fms/server.py  dead-man 핵심
def teleop_tick(self):                                 # 0.1 s 타이머
    v, w, t = self.teleop
    if time.time() - t < 0.4:
        self.teleop_active = True
        self.cmd_vel.publish(Twist(linear=Vector3(x=float(v)), angular=Vector3(z=float(w))))
    elif self.teleop_active:                           # 손을 뗌: 0 을 한 번 보내고 조용히
        self.teleop_active = False
        self.cmd_vel.publish(Twist())

4. Final Mission: 자연어 한 문장으로 부스 서빙 End-to-End (19강)

핵심 개념

LLM은 부스를 볼 수 없습니다. 그래서 WorldState(컵 위치표)를 글로 프롬프트에 넣어 주고, "이미 거기 있다" 같은 사실 판단은 LLM이 아니라 코드(check)가 합니다. LLM은 의도, 코드는 사실입니다.

WorldState.prompt()→PlanParser.parse (system = 규칙 + 표)→validate_world→world.check→확인 · 실행→world.apply (steps_done까지)

WorldState: 표 · 검사 · 갱신

함수하는 일
prompt()컵마다 현재 위치, 테이블마다 앉은 손님, 위치 규칙('~로'는 도착지, '원래 자리 · 제자리' = drinks)을 글로 만듦. 호출할 때마다 새로 생성
check(plan)표의 복사본(belief)으로 계획을 따라가며 pick 장소가 표와 다르면 문제, 놓을 곳에 이미 있으면 "이미 ...에 있다". 두 오류가 겹치면 쉬운 문장 하나만 남김. unknown · held 컵은 통과
apply(plan, steps_done, success)계획이 아니라 실제 끝난 단계(steps_done)까지만 반영. 실패한 바로 그 pick · place 단계의 컵은 UNKNOWN. 실행 전후 표를 history에 남김

'~로'는 도착지 · '원래 자리' = 음료대, 이 두 줄이 없을 때는 되돌리기 문장을 거절했습니다(6/8 → 8/8). 메시지 순서는 system(규칙 + 표) → 예시 → 이전 대화 → 이번 문장이며, world가 없으면 앞 절과 같은 프롬프트라 이전 예제도 그대로 동작합니다.

확인 포인트

  • 검사는 두 번입니다. validate_world(계획 자체의 모순) → world.check(위치표와의 모순). 단계는 있는데 문제가 있으면 LLM의 reply 대신 "그대로는 실행할 수 없습니다 (이유). 다시 말씀해 주세요."로 되묻습니다.
  • 시나리오마다 [world] 줄로 표가 어떻게 바뀌었는지 확인합니다.
남은 프로세스가 있으면 start가 멈춥니다. 실습을 끝낼 때 ./scripts/robotworld stop을 꼭 실행합니다.

5. 제어 기법 PID · LQR: 카트-폴 직접 튜닝 (20강)

핵심 개념

카트-폴은 조작할 수 있는 것이 카트 힘 u 하나인데 원하는 것은 둘(막대 세우기 + 카트를 목표 위치에)인 under-actuated 시스템입니다. 각도 PID는 막대 각도 하나만 보고, LQR은 위치 · 각도 · 속도 · 각속도 4개를 한꺼번에 봅니다.

세 제어기 비교

제어기구조관찰 결과 (원본 실험)
각도 PID막대 각도 오차만 0으로막대는 1초 안에 서지만 카트가 0.3 m/s로 밀려가고, 외란 뒤 약 5초에 레일 끝(±2.9 m)에서 넘어짐
캐스케이드 PID바깥 루프(위치 → 목표 각도) + 안쪽 루프(각도 PID), 이득 5개 수동Kx 0.05, Kv 0.1은 20 s에 x = 1.000 m로 멈춤 · Kx 0.1, Kv 0은 10 s에 x = 1.230 m로 출렁임
LQR비용 Q, R에서 K 4개 계산기본값으로 10 s에 x = 1.000 m, 외란도 받아냄. R=10이면 느려지고(약 12 s에 1 m), 3 N 외란에서 5.2 s에 넘어짐

이득 변화 예시입니다. Kd 0은 감쇠가 없어 ±5° 진동이 계속, Kp 15는 2.3 s 만에 넘어짐, Ki 50은 밀려남이 줄지만 외란을 넣으면 결국 넘어집니다.

target x ─▶[바깥 루프: 위치]─▶ θ_ref ─▶[안쪽 루프: 각도 PID]─▶ u ─▶ 카트-폴
             ▲ x, ẋ                       ▲ θ                         │
             └────────────────────────────┴───────────────────────────┘
pid.setpoint = -(kx * (x - target) + kv * x_dot)   # 바깥 루프 (위치 PD)
u = pid(theta, dt)                                  # 안쪽 루프 (각도 PID)
  • 부호가 반대인 이유(비최소 위상). 카트를 +x로 보내려면 먼저 −x로 살짝 빼서 막대를 +x로 기울여야 합니다. 마이너스 부호를 빼면 카트가 목표에서 멀어지며 넘어집니다.
  • 안쪽은 빠르게, 바깥은 느리게. 안쪽 Kp 60 · Kd 8, 바깥 Kx 0.05 · Kv 0.1. 안쪽이 바깥보다 대략 5~10배 빨라야 한다는 것은 일반적 경험칙입니다. Kv는 브레이크 역할입니다.
  • 캐스케이드도 상태 피드백. 펼치면 4개 상태에 이득을 곱해 더하는 구조입니다. 캐스케이드(손으로 맞춤) 3.0 / 60 / 6.4 / 8, LQR(Q = diag(10, 100, 1, 1), R = 0.1) 9.8 / 71.7 / 11.5 / 12.6 (위치 / 각도 / 속도 / 각속도).
# lqr.py 핵심: x[k+1] ≈ A x[k] + B u[k] (수치 미분)
mujoco.mjd_transitionFD(model, data, 1e-6, True, A, B, None, None)
P = solve_discrete_are(A, B, Q, R)
K = np.linalg.solve(R + B.T @ P @ B, B.T @ P @ A)
u = -K @ (np.concatenate([data.qpos, data.qvel]) - goal)

뿌리는 같습니다. LQR의 xᵀPx가 가치 함수이고 리카티 반복은 가치 반복과 같은 일을 합니다. 실무에서는 섞어 씁니다(강화학습으로 swing-up 후 LQR로 균형).

7. 정리

핵심 정리

  • LLM은 문장을 정해진 스키마(RobotCommand, RobotPlan)로 바꾸는 일만 맡고, Enum과 response_format으로 형식을, validate_world로 의미를 코드가 보장합니다.
  • 모호하거나 위험한 문장은 추측하지 않고 answer / 빈 steps + reply로 되묻거나 거부합니다.
  • Task Pipeline은 계획을 here · held로 따라가며 빠진 navigate를 자동으로 끼워 넣고, /execute_plan은 실패 단계에서 멈추고 steps_done · failed_step · spoken으로 보고합니다.
  • Web FMS는 SSE(0.2 s)로 상태를 밀어 주고, dead-man(0.4 s) · 서버 속도 제한 · cancel_all로 안전을 지킵니다.
  • Final Mission의 핵심은 "LLM은 의도, 코드는 사실"입니다. WorldState가 위치표를 프롬프트로 주고, check로 막고, apply로 실제 끝난 단계만 반영합니다.
  • 카트-폴에서 각도 PID는 카트가 밀려가고, 캐스케이드는 이득 5개를 손으로, LQR은 Q · R에서 4개 이득을 계산합니다. 반대 부호(비최소 위상)는 LQR의 K 안에 자동으로 들어갑니다.
  • Isaac Sim 이식은 브리지만 바꾸고 상위 스택을 그대로 씁니다. 실패 원인은 상위 코드보다 단순한 동역학 차이(armature, 접촉, 렌더 지연)에 있었습니다.
